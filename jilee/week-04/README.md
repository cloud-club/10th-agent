# [Week 4] 영업 회의록 에이전트 — 딜 기억과 긴 회의

Week 3에서 만든 회의록 에이전트에 **기억(Memory)과 긴 맥락(Context) 처리**를 더했다. Week 4 주제 "긴 작업에서 무엇을 기억해야 하는가?"에 대한 답은 이렇다. **회의록 전문이 아니라, 다음 회의에 필요한 사실만 따로 떼어 기억한다.** Week 3 구현은 [`jilee/week-03`](../week-03), 범위·결정 사항은 [작업정의서.md](./작업정의서.md)(12장: 판단 엔진 JEV 도입 검토), 설계 근거는 [기술정의서.md](./기술정의서.md)에 있다.

```text
녹취 ─▶ read_transcript ─(4천 자 초과)─▶ 구간별 정리(map) ─┐
딜 기억(state_N-1.json) ─▶ read_deal_context ───────────────┼─▶ LLM이 회의록 작성(reduce)
                                                           │
save_minutes ◀─────────────────────────────────────────────┘
  ├─ 규칙 검사 실패 → "저장 거부" 사유를 모델에 돌려줌 → 고쳐서 다시 저장
  └─ 통과 → minutes_N.md 저장 + 딜 기억 갱신(state_N.json) + 확보율·이행률 계산

외부 LLM 호출은 모두 MaskedLLM을 거친다: 한빛정밀 → [고객사A], 정수연 → [인물5] … 돌아온 답은 실명으로 복원
```

## Week 3 대비 바뀐 점

| 문제(Week 3) | Week 4 해결 | 위치 |
| --- | --- | --- |
| 직전 회의록 1건만 읽어서, 회차가 쌓이면 초반 합의가 사라짐 | 회차마다 **딜 기억 파일**을 남기고, 1~N-1차 누적 요약(참석자·합의·미합의·열린 액션아이템·Q코드 현황)을 읽음 | `agent/memory.py` |
| 확보율·이행률을 사람이 표를 다시 읽어서 셈 | 딜 기억에서 코드로 계산 | `memory.kpi` |
| 실행마다 규칙 위반이 들쭉날쭉(기한 없는 액션아이템, 8절 누락) | **저장 전 규칙 검사**. 위반하면 저장하지 않고 사유를 돌려보내 모델이 고쳐 쓰게 함 | `memory.validate` |
| 1,300자 넘는 녹취는 토큰 한도에 걸림 | 4천 자 넘으면 발화 단위로 잘라 구간별로 정리한 뒤 합침. 구간 사이 결정 번복은 [번복]으로 표시 | `tools.summarize_long_transcript` |
| 고객사명·인명이 그대로 외부 무료 API로 나감 | **마스킹**: 딜 폴더에서 이름 사전을 만들어 보내기 전에 가리고, 받은 뒤 되돌림 | `agent/masking.py` |

## 맥락을 어디에 두고 어떻게 꺼내나

| 층 | 무엇 | 저장 | 꺼내는 법 |
| --- | --- | --- | --- |
| 고정 지식 | 양식·표준 질문·작성 규칙, SOP | `knowledge/` | 매 실행 시스템 프롬프트, SOP는 `consult_sop`로 필요할 때만 |
| 장기 기억(딜 기억) | 참석자·회차별 합의·현재 미합의·열린 액션아이템·Q코드 현황 | `deals/{딜}/state/state_NN.json` | `read_deal_context`가 N-1차 스냅숏을 통째로 요약 |
| 관계(그래프) | 인물·회의·합의·액션아이템·Q코드를 점, 참석·담당·발생·점검·확보를 선으로 | `state/graph_NN.json` | 검색 질문에 아는 인물이 있으면 그 인물의 연결을 먼저 붙임 |
| 원문 근거 | 녹취 발화 한 줄, 회의록 항목 한 줄씩(맥락 꼬리표 부착) | 녹취·회의록 파일에서 색인 | `search_deal_history`: 필터 → BM25(2글자 조각) → RRF → 앞뒤 발화 → 최신성 표시 |
| 작업 기억 | 한 번 실행하는 동안의 대화 전체, 도구 호출, 저장 거부 사유, 모델·토큰 사용량 | `runs/{딜}/NN_시각.json`(마스킹된 상태, 저장소 제외) | 다음 실행에 넣지 않는다. 디버깅·평가·감사 추적용 |

현재 유효한 사실은 항상 딜 기억이 기준이고, 검색은 그 사실의 원문 근거를 찾는 용도다. 검색 결과가 딜 기억보다 앞선 회차면 "현재 사실은 딜 기억 기준" 표시가 붙는다.

### 검색 평가 (`experiments/search_eval/`)

D001 녹취 발화 119개에, 녹취와 표현을 다르게 쓴 질문 22개를 던져 정답 발화의 순위를 쟀다.

| 방식 | Recall@5 | MRR |
| --- | --- | --- |
| 띄어쓰기 단어 색인 | 0.727 | 0.548 |
| **한글 2글자 조각 색인(현재)** | **0.818** | **0.734** |
| 두 키워드 색인을 RRF로 결합 | 0.773 | 0.640 |

- 2글자 조각 색인이 조사 차이("선금은"·"선금이")를 흡수해 두 지표가 모두 올랐다.
- 키워드 검색 두 개를 RRF로 합치면 오히려 떨어졌다. 성격이 같은 검색끼리는 서로 보완하지 못한다. RRF는 키워드 검색과 의미 검색(벡터)처럼 **다른 종류의 검색**을 합칠 때 쓰는 것이 맞다. 벡터 검색은 `retrieval.VECTOR_RETRIEVER` 자리에 끼우면 같은 RRF 경로로 결합된다.
- 끝까지 못 찾은 질문은 모두 뜻은 같고 표현이 다른 경우다.
  - "도입 금액" ↔ "일억 이천에서 일억 오천"
  - "2년" ↔ "이 년"
  - "1년에 얼마" ↔ "연간 사백팔십만 원"
  - "누가 보냈는지" ↔ "내가 보낸 거 맞아"
- 다음 단계는 한국어 임베딩 검색 추가와 숫자 표기 통일(한글 숫자 → 아라비아 숫자)이다.

## 규칙 검사 항목

| 검사 | 위반 예 |
| --- | --- |
| 8개 절이 모두 있는가 | "## 5. 합의 사항" 누락 |
| 표의 칸 수가 헤더와 같은가 | 셀 안에 `\|`를 써서 칸이 밀림 |
| 액션아이템에 담당·기한이 모두 있는가 | 기한 "확인 불가" → 미합의로 옮기라고 반려 |
| 8절에 Q01~Q11이 한 행씩 있고 상태가 허용 값인가 | Q11 행 누락, 상태 "확보됨" |
| 이미 확보한 Q코드를 미확보로 되돌리지 않았는가 | 1차에서 확보한 Q05를 3차에서 "미확보"로 적음 |
| 참석자·담당자가 녹취·고객정보·이전 참석자에 있는 이름인가 | 녹취에 없는 "홍길동" |

Week 3에서 만든 3차 회의록을 이 검사에 넣으면 위반 3건(기한 없는 액션아이템 2건, 8절 형식)이 나온다.

## 실행

Python 3.12. 외부 패키지 설치 없음.

```bash
cd jilee/week-04
cp .env.example .env        # LLM 주소·키·모델 입력 (Groq 무료 기본, 폴백 OpenRouter 선택)

python app.py               # 로컬 앱 → http://localhost:8765
python run.py D001 4        # 4차 회의: 긴 녹취(5,829자, 3구간) + 1~3차 딜 기억
python run.py D001 1 --no-knowledge   # 비교 실험: 지식베이스·규칙 검사 없이
python -m unittest discover -s tests -t .   # 가짜 LLM 테스트 26건
python experiments/search_eval/eval_search.py   # 딜 이력 검색 평가(Recall@5·MRR)
```

비교 실험용 스위치는 `agent/tools.py`에 있다. `MEMORY_MODE = "last"`로 바꾸면 Week 3 방식(직전 회의록 1건)으로 돌아가고, `.env`에 `MASKING=off`를 주면 마스킹을 끈다.

## 테스트 데이터

`deals/D001/transcript_04.txt`는 Week 4용으로 새로 만든 4차 회의 녹취다. 계약 조건을 협의하는 자리로, 아래 요소를 일부러 넣었다.

- 영어 약어: PPAP·MSA·MES
- 결정 번복 2건

  - 자료 기한을 12월 셋째 주 → 12월 26일로 변경

## 한계

- 마스킹은 사전에 있는 표기만 가린다. "정팀장님"처럼 성+직함으로 부르는 경우와 STT가 잘못 받아 적은 이름(사전에 없는 것)은 그대로 나간다. 실제 회사 데이터는 기업용 API 계약 뒤에 쓴다.
- Week 3 형식(목록형 8절) 회의록은 근거 없이 Q코드만 복원된다. 새 형식 회의록부터 근거가 함께 쌓인다.
- 지난 액션아이템 짝짓기는 문자열 유사도로 한다. 표현이 크게 바뀌면 새 항목으로 잡힐 수 있다. 작업정의서 12장의 판단 엔진(JEV) 적용 후보다.
- 검색은 아직 키워드(BM25)뿐이다. 뜻은 같고 표현이 다른 질문(금액 범위, "2년"과 "이 년")을 놓친다. 벡터 검색은 외부 임베딩 API를 쓰면 마스킹을 먼저 거쳐야 하므로 회사 환경(AWS) 구성과 함께 붙인다.
- 그래프는 딜 기억을 옮긴 것이라 "합의 ↔ 인물"(누가 결정했나) 선은 아직 없다. 회의록 5절에 결정자를 적는 양식 변경이 필요하다.
- 실제 LLM으로 4차(긴 녹취) 실행 결과는 아직 측정 전이다.
